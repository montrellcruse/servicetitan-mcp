# v3.0.1 plan for an overall Glama A

Status: implementation and all 264 independent definition reviews complete on `codex/v3.0.1-glama-a`; Node 22/24 release validation, package consumers, and protocol refresh pass. The PR will be submitted for review. The user will handle the main-branch merge after reviews; publication and external Glama confirmation remain pending. Final local targets pass (mean 4.4114, minimum 4.0, projected overall 3.7); the fixed selection corpus passes 41/41 on both baseline and candidate.

## Outcome and release scope

Make the existing ServiceTitan tools easier for agents to select and invoke correctly, with accurate descriptions and practical installation profiles. Target an overall Glama A for the next patch, `3.0.1`, from `3.0.0` at `bb8bdd1`. Definition quality should also reach A; this does not require every coherence submetric to reach A.

The recommended approach is a compatible description, documentation, and metadata patch with full-catalog evaluation and an explicit overlap audit. A smaller change limited to the lowest-scoring exports would leave widespread ambiguity unresolved. A redesign that removes duplicate names or changes the default profile could improve tool-count scoring, but would change existing discovery. A separate follow-on discovery track is defined below.

Compatibility requirements:

- Preserve every existing tool name, profile membership, default setting, validation constraint, operation annotation, handler, API route, and response behavior.
- Keep 264 tools in default readonly discovery and 458 tools with explicit experimental opt-in: 261 API-backed reads, three system tools, and 194 experimental mutations.
- Keep `ST_TOOL_PROFILE=full` as the default. Recommend explicit focused profiles in onboarding.
- Retain the `readonly-v1` support boundary and experimental write safeguards.
- Review and evaluate all 264 read-tool descriptions. Prioritize the weakest scores, then continue through the 247 tools currently below 4.0, including B-rated and lower A-rated definitions. Preserve descriptions already meeting the quality and accuracy standard. Review mutation text affected by shared parameter descriptions, without expanding the patch into a mutation rewrite.
- Keep dependencies, pinned API contracts, and runtime request logic outside this patch. Description corrections that expose a behavioral defect must be recorded and separately scoped.

## Baseline and success measures

The live [Glama scorecard](https://glama.ai/mcp/servers/montrellcruse/servicetitan-mcp/score), inspected September 5, 2026 Phoenix time, grades the v3 default surface. It reports definition quality C (mean displayed as 3.2/5, minimum 2/5), coherence C, maintenance A, license A, and profile completion 58%. Coherence dimensions are disambiguation 2, naming 3, count 1, and completeness 4 out of 5. The individual grades total 115 C, 69 B, and 80 A.

Local SDK `tools/list` inspection used dummy credentials and made no upstream calls. Bytes below measure UTF-8 `JSON.stringify(tools)`, excluding the surrounding protocol envelope; they are not token estimates.

| Configuration | Read tools | Discovery bytes | Description bytes |
| --- | ---: | ---: | ---: |
| Default / full | 264 | 283,857 | 11,244 |
| CRM | 33 | 35,377 | 1,287 |
| Dispatch | 75 | 83,450 | 2,180 |
| Analytics | 34 | 36,706 | 5,615 |

243 default descriptions contain fewer than eight whitespace-separated words. This is an inventory signal, not a quality threshold. The 44 `export_*` tools have a mean displayed tool score of approximately 2.72 and are the first large improvement batch. Across the complete catalog, 247 tools score below 4.0; improving only the 115 C-rated tools is insufficient for the recommended target.

The [published scoring rule](https://glama.ai/mcp/servers/montrellcruse/servicetitan-mcp/score) is:

```text
Definition quality = 0.60 * mean tool score + 0.40 * minimum tool score
Overall quality = 0.70 * definition quality + 0.30 * coherence
A threshold = 3.50 / 5
```

Current coherence is `(2 + 3 + 1 + 4) / 4 = 2.5`. Use that unchanged value for conservative projections rather than assuming a coherence improvement.

| Measure | Working target |
| --- | --- |
| Mean individual read-tool score | At least 4.3/5 |
| Lowest individual read-tool score | At least 4.0/5 |
| Resulting definition quality at those targets | 4.18/5 — A |
| Projected overall with coherence held at 2.5 | 3.676/5 — A |
| Independent accuracy review | All 264 reads reviewed; no unresolved material errors |
| Final external outcome | Glama reports A for overall and definition quality on the released full surface |

For comparison, a 4.0 mean and 3.5 minimum would produce an overall 3.41, still B at current coherence. The weakest tool materially affects the result, so evaluation must cover the entire catalog. Use unrounded values when available and retain a buffer above 3.5.

The numeric targets guide pre-release evaluation; they are not a guarantee that a local evaluator will match Glama. Release readiness also requires compatibility, factual accuracy, selection evidence, working examples, and passing repository gates. Keep the overall-A objective open until the live evaluation confirms it. Profile completion, related servers, and observed usage are separate from the quality formula. The tool-count score may remain low because full discovery remains compatible.

## Work package 2: establish and apply the description standard

Maintain descriptions at their current registration sites in `src/domains/**` and `src/server.ts`; keep `TOOLS.md` generated from the registry. Add the authoring guidance to `CONTRIBUTING.md` so it ships with existing maintained documentation.

Use all six [Glama definition-quality dimensions](https://glama.ai/blog/2026-04-03-tool-definition-quality-score-tdqs) during authoring and evaluation: purpose, usage guidance, behavior, parameter semantics, conciseness/structure, and contextual completeness. Their scorecard weights are 25%, 20%, 20%, 15%, 10%, and 10%, respectively. Each description should supply the information necessary for that tool:

1. A concrete action and resource, including what a returned record represents when ambiguous.
2. When to choose it, and the nearest alternative when that decision is non-obvious.
3. Important input relationships or prerequisites that schema structure alone cannot explain.
4. Relevant execution behavior: single page versus automatic pagination, continuation, freshness/cache, report scheduling, completeness, or result retrieval.

Prefer a few concise sentences. Add an example only when it resolves a real invocation ambiguity. Keep bounds, defaults, and formats in parameter descriptions where possible; avoid repeating every schema field or safety annotation in prose. Do not impose universal word-count gates or append generic warnings to every tool.

Execution order:

- Correct unsupported claims immediately, including `intel_revenue_summary` dashboard-parity wording and unqualified latency estimates in `src/domains/intelligence/revenue.ts`. Explain report timing from current scheduling behavior, and preserve the README's company-validation limits.
- Improve the 44 supported generic exports in `src/domains/export/exporters.ts`, starting with location contacts, activities, adjustments, business units, calls, leads, memberships, and payments. State verified incremental-export semantics and distinguish export feeds from filtered interactive lists.
- Address low-scoring accounting, dispatch, CRM, inventory, and other list tools, especially `accounting_payments_list`, `dispatch_arrival_windows_list`, and `crm_bookings_list`.
- Continue through the remaining tools below 4.0; improve B-rated and lower A-rated definitions against the same standard. Re-evaluate all reads, including all ten intelligence tools, for accuracy, alternatives, pagination, completeness, and stale claims. High scores do not exempt a description from this review.

Verify ordinary list tools individually before saying they retrieve all results. Export cursor rules must come from the associated operation rather than a universal assumption about `from`. Explain large-result retrieval only where it materially affects using the tool; the system tool retains full retrieval instructions.

Implementation constraint: `scripts/check-contracts.mjs` inventories `registerExportTool(...)` using a regex that expects a one-line call with literal name, description, and path arguments. Preserve that supported registration shape in this patch. If an implementation needs multiline calls or composed descriptions, update the inventory parser deliberately and add a fixture proving the expected export operations remain covered. Passing the checker after silently dropping factory entries is unacceptable.

Done when all 264 reads have a completed independent accuracy review, every ambiguous family has usable selection guidance, generated documentation agrees with discovery, and the final evaluation round supports the A-target measures. Use the evaluation loop below to resolve remaining weak definitions rather than stopping after the initial C-rated batch.

## Work package 3: resolve duplicate and overlap ambiguity

These four equivalent export pairs are confirmed starting points for the full-catalog audit, not a claim that every duplicate has been found. Keep both names available in this patch:

| Generic export | Domain export | Guidance |
| --- | --- | --- |
| `export_employees` | `people_employees_export` | Same employee feed; cross-domain sync versus People workflows. |
| `export_activity_codes` | `settings_activity_codes_export` | Same activity-code feed; cross-domain sync versus Settings workflows. |
| `export_activities` | `settings_activities_export` | Same activity feed; explain the timesheet-related resource using the pinned contract. |
| `export_tag_types` | `settings_tag_types_export` | Same tag-type feed; cross-domain sync versus Settings workflows. |

Descriptions should identify the equivalent name and explain that fetching both duplicates the same feed. Prefer `export_*` in cross-domain bulk-sync guidance and the domain-specific name within domain workflows. Alternatives can be absent under profiles and allowlists: guidance must remain useful when only one equivalent is exposed. Neither name becomes deprecated or hidden in this patch, and no handler-forwarding alias framework is needed.

Explain these distinct operations separately:

- `marketing_calls_v3_list` and `marketing_calls_v2_list`: recommend v3 for ordinary call search using its supported filters; explain when the v2 filter contract is required. Preserve different ID representations, active flags, and sorting inputs. Do not merge or normalize their schemas.
- `dispatch_job_cancel_reasons_list`: the paginated, filterable cancellation-reason catalog.
- `dispatch_jobs_cancel_reasons_list`: the Jobs cancellation-reason lookup for known IDs. Preserve its separate path, scope, and documented ID limit.
- `marketing_campaign_costs_list` and `marketing_campaigns_costs_list`: broader cost searches versus a specific campaign's costs; preserve their distinct paths and filters.
- `payroll_timesheets_job_list` and `payroll_timesheets_jobs_list`: one job's timesheets versus queries across jobs; preserve required IDs and serialization.
- Export/list/get families: describe incremental synchronization, filtered browsing, and known-ID retrieval as distinct tasks when the associated implementation supports that distinction.

Confirm these distinctions against the pinned operation before finalizing copy. Keep undocumented, excluded tools excluded.

Done when every overlap candidate has been classified, every confirmed equivalent family has reciprocal guidance, each distinct family has an evidence-backed selection rule, and compatibility checks show unchanged names, routes, and inputs. Additional pairs discovered during the audit follow the same policy. Sharing an implementation is a separate refactor and would not reduce the number of advertised choices.

Collapsing the four currently confirmed pairs would reduce full discovery from 264 to 260. That can improve selection clarity, but substantial reductions require focused discovery. Do not assume duplicate cleanup alone solves Glama's tool-count criticism.

## Follow-on track: optional canonical discovery

Plan this as a separate feature release after the compatible patch. Its purpose is to remove redundant choices from discovery while preserving a clear compatibility path, regardless of whether v3.0.1 already achieves overall A.

- Add an opt-in mode that selects one preferred name per proven equivalent family only after readonly, profile, and domain filtering. Keep default legacy discovery unchanged initially. A domain-only configuration must retain the equivalent that actually belongs to that domain.
- Honor explicit `ST_TOOLS`: expose the requested available name, and both names if both were explicitly requested. A preference rule must not substitute a tool outside the user's configured domain/profile intersection.
- Use a deterministic, evidence-backed equivalence map with schema/request tests. Resolve selection before registration so results do not depend on module load order. Keep distinct API versions and lookup scopes distinct.
- The currently installed SDK has no public hidden-but-callable alias facility: omitting or disabling a registered name also removes its callable behavior. Do not promise transparent legacy calls, patch private SDK state, or replace protocol handlers as a shortcut. Document the callable surface of the opt-in mode and verify it over the wire.
- Measure actual selection improvements and discovery bytes for each mode. Publishing an optional mode does not by itself change the default catalog Glama grades. Changing the default or removing legacy names requires a separate migration/versioning decision with tests for existing configurations.

This follow-on work is not a prerequisite for a mathematically achievable overall A and is not part of the 264-tool-compatible patch acceptance criteria.

## Suggested implementation order

One focused patch PR can contain five reviewable commits:

1. Baseline compatibility evidence, full-catalog overlap inventory, evaluation inputs, and description authoring guidance.
2. Read descriptions, equivalent/distinct-endpoint guidance, and focused regression updates.
3. Independent accuracy review, selection evaluations, weakest-tool revisions, and final full-catalog scoring evidence.
4. Profile onboarding, Glama manifest/fingerprint coverage, and regenerated catalog.
5. Version/changelog, final validation results, acceptance evidence, and fingerprint.

Domain description batches can proceed in parallel after the standard and overlap rules are agreed; the final accuracy/evaluation reviewer should be independent of the authors. One owner should edit the shared export factory, catalog generator, and release evidence to avoid conflicting changes. The optional canonical-discovery feature uses a separate design and PR. No version bump or implementation change is part of this planning artifact.
